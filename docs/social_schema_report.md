# Отчёт по моделям ДвижМАКС

## Объём изменения

20 таблиц: 9 существующих таблиц каталога и 11 новых таблиц пользователей,
поиска компании и уведомлений. Каталог и миграция `0001_catalog` не изменены.
Новая миграция: `0002_social`, предыдущая версия: `0001_catalog`.
Модели добавлены в `infrastructure/db/social_models.py` и зарегистрированы
в общем `Base.metadata` через импорт в `infrastructure/db/__init__.py`.

Это только схема хранения: обработчиков maxapi, сервисов, подключения async,
worker отправки, начисления весов и автоматического создания матчей пока нет.
Схема совместима с AsyncSession. Relationships пользователя используют
`lazy="raise"`: загрузка через `selectinload` или явные запросы, без скрытого I/O.

## Новые модели

| Модель / таблица | Назначение и ограничения |
|---|---|
| User / users | MAX ID уникален; username необязателен и не является ключом. Анкета в той же таблице. Гость может иметь незаполненные поля. Для active нужны имя, пол, возраст, город и фото. Возраст 1–120 — техническая проверка, не возрастная политика продукта. |
| UserConsent / user_consents | История принятия/отзыва версий согласия; одно неотозванное согласие на пользователя и версию. Повторное согласие после отзыва создаётся новой записью. |
| UserTagWeight / user_tag_weights | Стартовый и накопленный веса по паре пользователь–тег. Вклад реакций может быть отрицательным. Отсутствующая запись означает ноль. |
| EventReaction / event_reactions | Одна реакция like/dislike/skip на пару пользователь–событие. Любая запись исключает событие из рекомендательной ленты. |
| EventPlan / event_plans | Один постоянный план на пару пользователь–событие, выбранные день/время и отдельное состояние поиска компании. Время требует даты. Искать можно только при planned. |
| CompanionView / companion_views | Уникальная тройка viewer_id + event_id + shown_user_id. Направленный показ в поиске: А видел Б не означает, что Б видел А. Самопоказ запрещён. |
| CompanionInterest / companion_interests | Направленный интерес между двумя планами. Составные FK гарантируют одинаковое событие. Уникальная пара планов; интерес к себе запрещён. Даты просмотра и анонса независимы. |
| Match / matches | Уникальная пара пользователей по событию. UUID участников записываются по возрастанию. Составные FK требуют наличия обоих планов на это событие. Наличие взаимных лайков проверяет сервис. |
| UserBlock / user_blocks | Уникальная направленная блокировка. Самоблокировка запрещена. В поиске проверяются оба направления. |
| Notification / notifications | Очередь только сводок входящих интересов и матчей. Уникальный deduplication_key; одно pending/processing уведомление-сводка на получателя и событие; одно уведомление матча на получателя. |
| NotificationInterest / notification_interests | Точный состав сводки. Интерес закрепляется максимум за одним уведомлением; при окончательной отмене неотправленного уведомления связи освобождает сервис. |

## Реакции и рекомендации

`like` даёт +1, `dislike` −0.5, `skip` 0 всем назначенным тегам события.
При замене реакции сервис применяет разницу: like → dislike означает −1.5.
Повторное действие не начисляет вес второй раз. Изменение реакции и весов
выполняется одной транзакцией с защитой от конкурирующих запросов.

Начальный вес хранится отдельно. Итог = initial_weight + reaction_weight.
Коэффициент 0.4 для вторичных тегов применяется при сортировке, не при накоплении.
Удаление лайка из понравившихся переводит реакцию в skip, а не удаляет запись:
так событие не возвращается в ленту. План остаётся независимым от реакции.

## Планы и анкеты

«Пойду» создаёт/активирует EventPlan; поиск компании включается отдельно.
Отмена плана выключает поиск, но не убирает лайк. План не пересоздаём физически:
иначе старые ссылки интересов потеряют смысл. На MVP один план на событие,
не несколько независимых посещений разных сеансов.

Публичный поиск требует active-профиля, действующего согласия, planned-плана,
company_status=looking, совместимости дат и отсутствия блокировки.
Большинство этих условий межтабличные и проверяются сервисом.
Описание необязательно; фото задаётся ссылкой или вложением. Валидность ссылки,
фото, username и текста проверяется при вводе, CHECK проверяет только наличие.
Справочник значений пола ещё не фиксируется: поле String(30).

В поиске анкет исключаем уже показанных по CompanionView. После успешной отправки
сохраняем показ; параллельные нажатия сериализует обработчик. БД не может атомарно
объединить отправку в MAX и запись показа: при аварии между ними повтор возможен.
Это принятое ограничение MVP без очереди входящих событий.
Повторное открытие из входящих интересов и отправка при матче разрешены.
CompanionView не заменяет viewed_at: первое — показ в поиске, второе — просмотр
конкретного входящего интереса.

## Матчи

Для создания Match проверяются два встречных active-интереса по одному событию,
актуальность планов и отсутствие блокировок. UUID сортируются перед вставкой.
Уникальность защищает от двух матчей при одновременных лайках.
В той же транзакции создаются два Notification(type=match), по одному каждому.
Порог три к матчу не применяется. Отправляем анкету и доступный способ связи,
но не создаём чат автоматически. Возможность ссылки на пользователя без username
нужно проверить при интеграции с MAX.

При отмене/переносе плана сервис должен погасить неактуальные интересы и уведомления.
Повторное включение поиска не должно молча восстанавливать старые withdrawn-интересы.
История показов сохраняется. Правила повторного открытия закрытого матча пока
не реализованы: новый дубль БД не допускает.

## Уведомления 3+

1. Считаем разных отправителей по событию: интерес active, не просмотрен,
   не анонсирован, планы актуальны, нет блокировок и связи с другой сводкой.
2. При трёх и более создаём одно pending-уведомление. Новые интересы можно
   присоединять к pending-сводке. После перехода в processing состав фиксируется.
3. Worker перед отправкой повторно проверяет актуальность и настройки пользователя.
   Если подходящих людей стало меньше трёх, сводку отменяет и освобождает связи.
4. При успешной отправке в одной транзакции устанавливает sent и announced_at
   только для вошедших в сводку интересов. Новые лайки не отмечает автоматически.
5. Временные ошибки повторяются с ограничением попыток. После окончательной отмены
   освобождаются неанонсированные связи. Дубликат внешней отправки при потере ответа
   MAX полностью исключить нельзя.

Кнопка входящих интересов показывает анкеты даже при одном-двух лайках и независимо
от announced_at. Просмотр одной анкеты ставит viewed_at только её интересу.
Обычные ответы на кнопки отправляются напрямую через maxapi, не через Notification.
Согласованность получателя/события сводки с её интересами и участниками матча
проверяет сервис при постановке: одни FK этого не проверяют.

## Миграции и проверки

`python -m alembic upgrade head` применяет 0001 → 0002 к существующей PostgreSQL.
`python -m alembic downgrade 0001_catalog` удаляет только новые таблицы и их данные.
`python -m alembic upgrade head --sql` позволяет просмотреть SQL без подключения.

`python -m unittest discover -s tests -v` проверяет соответствие замороженных миграций
моделям, PostgreSQL SQL применения/отката, ключи неповторных показов и настройки ORM.
Эти проверки не заменяют запуск на настоящей PostgreSQL. Docker Engine локально
недоступен, поэтому миграции к живой БД не применялись; сервер не использовался.

## Что сознательно не добавлено

Нет входящей очереди, истории попыток ИИ, версий промпта, автоматических групп,
внутреннего чата, feedback и сложной аналитики. Нет автокаскадного удаления данных;
отзыв согласия/удаление пользователя потребуют отдельного явного сценария очистки.
Все ID генерируются SQLAlchemy, статусы ограничены CHECK, даты — TIMESTAMPTZ.
Поля локального дня и времени плана интерпретируются в часовом поясе города события.
